# 结构保持示例

本文档展示如何完全保持原始需求文档的目录结构。

## 示例1: 保持页面结构

### 原始需求文档结构

```markdown
# 用户管理模块
## 用户注册页面
### 邮箱输入
用户需要输入邮箱地址...

### 密码设置
用户需要设置密码...

## 用户登录页面
### 登录表单
用户输入邮箱和密码...
```

### ✅ 正确的功能梳理（保持原结构）

```markdown
# 用户管理模块
## 用户注册页面
### 邮箱输入
#### 邮箱格式校验
- 输入标准邮箱格式（user@example.com）
  - 预期：格式校验通过，允许提交
- 输入缺少@符号（userexample.com）
  - 预期：提示"邮箱格式不正确"

#### 邮箱长度限制
- 输入254字符的邮箱
  - 预期：校验通过，正常保存
- 输入255字符的邮箱
  - 预期：提示"邮箱长度超过限制"

### 密码设置
#### 密码强度校验
- 输入8位数字+字母组合
  - 预期：校验通过
- 输入少于8位
  - 预期：提示"密码长度至少8位"

## 用户登录页面
### 登录表单
#### 邮箱输入
- 输入已注册的邮箱
  - 预期：允许继续输入密码
- 输入未注册的邮箱
  - 预期：提示"该邮箱未注册"
```

**说明**: 
- ✅ 保持了原文档的三级结构：模块(#) → 页面(##) → 功能区(###)
- ✅ 在原结构下添加了四级标题(####)来描述具体功能点
- ✅ 使用列表项描述测试场景

### ❌ 错误的功能梳理（重新组织了结构）

```markdown
# 用户管理模块
## 邮箱验证
### 邮箱格式校验
- 输入标准邮箱格式（user@example.com）
  - 预期：格式校验通过

### 邮箱长度限制
- 输入254字符的邮箱
  - 预期：校验通过

## 密码管理
### 密码设置
#### 密码强度校验
- 输入8位数字+字母组合
  - 预期：校验通过

### 密码登录
- 输入正确密码
  - 预期：登录成功
```

**问题**: 
- ❌ 改变了原文档的结构（将"用户注册页面"和"用户登录页面"重组为"邮箱验证"和"密码管理"）
- ❌ 失去了与原文档的映射关系
- ❌ 难以追溯到原需求文档的对应位置

## 示例2: 保持流程结构

### 原始需求文档结构

```markdown
# 申卡流程
## 前置条件校验
### 钱包开户状态校验
用户必须完成钱包开户...

### 刷脸Token校验
用户需要有效的刷脸Token...

## 申卡提交
### 提交申卡请求
用户点击申卡按钮...
```

### ✅ 正确的功能梳理（保持原结构）

```markdown
# 申卡流程
## 前置条件校验
### 钱包开户状态校验
#### 开户状态检查
- 用户未完成DTC渠道开户
  - 预期：无法进入申卡流程，提示"请先完成钱包开户"
- 用户已开户但KYC未验证通过
  - 预期：无法进入申卡流程，提示"请先完成KYC验证"
- 用户已开户且KYC已验证通过
  - 预期：可以正常进入申卡流程

### 刷脸Token校验
#### Token有效性检查
- 用户从未进行过刷脸验证
  - 预期：提示完成刷脸验证，跳转到刷脸页面
- 用户刷脸Token已过期
  - 预期：提示完成刷脸验证，跳转到刷脸页面
- 用户刷脸Token有效
  - 预期：可以直接提交申卡请求

## 申卡提交
### 提交申卡请求
#### 提交按钮状态
- 所有前置条件校验通过
  - 预期：提交按钮可点击
- 任一前置条件校验未通过
  - 预期：提交按钮置灰不可点击
```

**说明**: 
- ✅ 完全保持了原文档的结构：流程(#) → 阶段(##) → 检查点(###)
- ✅ 标题名称与原文档完全一致
- ✅ 在原结构下添加了功能细节

## 结构保持的核心原则

### 1. 完全映射原始结构
- 原文档有几级标题，输出就保持几级标题
- 原文档的标题名称，输出完全使用相同名称
- 原文档的章节顺序，输出保持相同顺序

### 2. 只添加不重组
- 可以在原结构下添加更深层级的标题来描述功能细节
- 可以在原标题下添加列表项来描述测试场景
- 不能改变原有的标题层级关系
- 不能合并或拆分原有的章节

### 3. 保持可追溯性
- 任何人看到输出文档的某个章节，应该能立即在原文档中找到对应位置
- 标题名称应该作为"锚点"，保持与原文档的一致性
- 如果原文档使用特定术语（如"ME Page"、"Security Page"），输出必须使用相同术语

### 4. 识别文档类型
不同类型的需求文档有不同的结构模式：

**UI/UX需求**: 通常按页面组织
```
# 模块
## 页面名称
### UI组件/功能区域
```

**业务流程需求**: 通常按流程阶段组织
```
# 业务流程
## 流程阶段
### 检查点/操作
```

**功能需求**: 通常按功能分类组织
```
# 功能模块
## 子功能分类
### 具体功能
```

识别文档类型后，严格遵循其原有的组织方式。
